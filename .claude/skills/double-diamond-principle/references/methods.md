# 方法選擇與證據品質

需要挑選研究、綜合、原型或驗證方法時使用。方法服務於要回答的問題；不是每個專案都要完成的清單。

## 關鍵字與層次

| 概念 | 決策用途 |
| --- | --- |
| divergent thinking／發散 | 擴大問題理解或解法範圍，延後過早選定 |
| convergent thinking／收斂 | 根據需要、證據與限制聚焦並採取行動 |
| observation／觀察 | 實際看見或記錄的事件；與解釋分開 |
| insight／洞察 | 從證據得到、會改變設計判斷的理解，保留推論鏈 |
| assumption／假設 | 尚待驗證但會影響決策的前提 |
| design brief／設計任務說明 | 目標對象、情境、挑戰、範圍、限制與成功判準 |
| co-design／共同設計 | 受影響者與相關角色實際參與形成方案，不只是收到通知 |
| prototype／原型 | 用來回答特定問題的可試驗表現形式，不一定是程式 |
| pilot／試行 | 在受限的實際情境中驗證交付與結果 |
| outcome／成果 | 對人的行為或處境造成的改善；與完成文件、上線功能等產出區分 |
| feedback loop／回饋循環 | 把使用及交付中的學習帶回下一輪決策 |

發散／收斂依 [Framework for Innovation](https://www.designcouncil.org.uk/resources/framework-for-innovation/)；brief 與兩個鑽石的用法見 [官方歷史](https://www.designcouncil.org.uk/resources/the-double-diamond/history-of-the-double-diamond/)。證據分類與成果判讀是本 skill 的實務整理。

框架的 Methods Bank 以 **Explore、Shape、Build** 組織方法：探索挑戰與機會、形塑洞察與原型、建立想法與能力。這三類不是 Discover／Define／Develop／Deliver 的替代階段，也沒有強制的一對一對應。同一方法可以服務不同階段。

## 探索與綜合

| 要回答的問題 | 可選方法 | 最小做法與限制 |
| --- | --- | --- |
| 現有資料能說明什麼？ | 次級研究、現有服務紀錄 | 記來源、日期、對象、計算口徑與缺漏；其他情境的結論不直接當成本專案事實 |
| 人們實際怎麼做？ | 情境觀察、訪談 | 聚焦具體任務與近期經驗，用開放且不誘導的問題；記行為與說法差異 |
| 行為如何隨時間改變？ | 使用者日誌 | 讓參與者記事件與情境，再分析模式；回憶與記錄負擔會影響資料 |
| 哪些人的經驗還沒被看見？ | 取樣規劃 | 依研究問題找行為／情境差異，包括非使用者或極端情境；探索性樣本不是人口比例估計 |
| 線索很多，重要模式在哪？ | 分群、比較筆記、優先排序 | 讓每個主張連回原始資料；相似敘述可合併，但保留差異與反例 |
| 問題發生在流程哪裡？ | 使用者旅程圖 | 畫出任務、接觸點、障礙與前後關係；沒有證據的片段標為假設 |
| 什麼阻礙執行？ | Drivers and hurdles、利害關係人討論 | 分清限制、偏好與可改變條件；團隊共識不自動證明使用者需求 |

方法來源：[Design Methods Step 1: Discover](https://www.designcouncil.org.uk/our-work/projects-programmes/archive/article/design-methods-step-1-discover/)、[Step 2: Define](https://www.designcouncil.org.uk/our-work/projects-programmes/archive/article/design-methods-step-2-define/)。表格的來源標記與推論限制是本 skill 補充的操作方式。

## 發展與驗證

| 要回答的問題 | 可選方法 | 最小做法與限制 |
| --- | --- | --- |
| 還有哪些不同解法？ | 腦力激盪、快速草圖、類比靈感 | 先發散再評選；依問題探討不同作用機制，沒有固定的想法數量要求 |
| 哪個方案值得下一步？ | Assessment criteria／評選準則 | 先談準則與限制，再比較選項；區分硬限制和可權衡條件，分數及權重標示為判斷而非實測 |
| 不同人會如何使用？ | 人物輪廓、情境、storyboard | 以研究支持的差異為主；腦力激盪或 AI 生成輪廓標明是假想情境，不能當真人證據 |
| 服務前後台能接上嗎？ | Service blueprint／服務藍圖、角色演練 | 連結使用者接觸點、執行者、後台與依賴；演練用來找問題，不能冒充現場使用者測試 |
| 人能理解或完成關鍵任務嗎？ | 紙本、實體或互動原型 | 決定要測的假設，再選足夠精度；區分「外觀像」與「行為能運作」 |
| 實際交付是否可行？ | 小規模試行、情境測試 | 記錄對象、條件、協助程度及失敗；同時觀察受益與副作用 |
| 擴大後是否持續改善？ | 分階段交付、評估、回饋渠道 | 以可觀察結果決定擴大／修改／停止，確認後續負責人 |

方法來源：[Step 1: Discover](https://www.designcouncil.org.uk/our-work/projects-programmes/archive/article/design-methods-step-1-discover/)、[Step 2: Define](https://www.designcouncil.org.uk/our-work/projects-programmes/archive/article/design-methods-step-2-define/)、[Step 3: Develop](https://www.designcouncil.org.uk/our-work/projects-programmes/archive/article/design-methods-step-3-develop/)、[Step 4: Deliver](https://www.designcouncil.org.uk/our-work/projects-programmes/archive/article/design-methods-step-4-deliver/)。方法不被其文章所在階段限制。

## 少量、可追溯的記錄

需要時將以下欄位併入現有筆記，而非預設另建檔案或系統。

**證據記錄**：來源／日期；對象與情境；實際觀察或原話；解釋；限制或反證；影響哪個決策。原話只有在確實取得時才加引號，未取得資料留待驗證。

**工作 brief**：誰在什麼情境需要什麼改善；目前遇到什麼阻礙；有哪些證據；本次處理與不處理的範圍；限制；如何辨識改善。

**驗證卡**：要驗證的假設；原型版本；測試任務與對象；觀察方式／基線；事先提出的判斷條件；實際結果；採用、修改、捨棄或回返哪個問題。只有規劃時，結果欄明確標為未執行。

這三種記錄是本 skill 的操作設計，不是 Design Council 強制模板。依情境使用簡短段落、表格或現有工作項目即可。

## 避免證據被放大

- 少數受訪者的經驗可揭露障礙與機制；若要聲稱盛行率、群體偏好或成效，需要相應的樣本與研究設計。不可把質性線索的出現次數直接當成人口比例。
- 既有統計需保留分母、期間與群體；不同來源或互相重疊的分類不能直接相加。前後改善也可能受其他條件影響。
- 偏好、完成任務與在日常環境獲益是不同訊號。測試時得到的協助、任務順序與情境都可能影響結果。
- 明確限制可以淘汰方案；對效果仍未知時，記為未知並設計測試，不用任意數字補滿評分表。
- 決策所需證據已足夠時向前推進；不足時先選能改變決策的最小研究，而非無限擴大探索。

以上是為避免誤用研究結果而加入的操作準則；不把歷史指南中的樣本人數、brainstorm 數量或 rollout 人數當成通用門檻。
